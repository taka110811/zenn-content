社内の次世代データ基盤（ハブドメイン）を模して、私用Azure上に **Azure Databricks 最小構成** を週末ラボとして一巡した記録です。

ゴールは「安く・小さく・設計の意味が残る」こと。バックエンド Private Link やログ5年保管は意図的に省略しています。

## 何を再現し、何を省いたか

| 社内設計 | 私用ラボ |
|---|---|
| ドメイン単位の個別サブスクリプション | サブスク1つなので **RG = ドメイン** に読み替え |
| VNetインジェクション + public/private | **再現**（`172.16.0.0/22` + `/24`×2） |
| SCC（クラスターにパブリックIPなし） | **再現**（`no_public_ip = true`） |
| バックエンド Private Link | **省略**（常時課金を避ける） |
| UC用ストレージ別建て（WSカタログ不使用） | **再現**（設計の肝） |
| IPアクセスリスト / NCC | 任意・画面確認（今回アカウントコンソールは未到達） |

### なぜ共用サブスク／共通VNetに載せないのか

Databricks がサブネットに付ける NSG は、送受信とも `VirtualNetwork` 許可が入ったまま **更新・削除できない**。  
共通VNetに同居すると、他システム経由のアウトバウンドを自分たちで塞げないリスクがある。

だから社内は「個別サブスク + Databricks専用VNet」。私用では専用VNetだけ忠実に再現した。

## 構成図（完成形のイメージ）

```text
lab-rg-dev-jpe
 ├ lab-vnet-dev-jpe (172.16.0.0/22)
 │  ├ lab-snet-public-dev-jpe  (ホストサブネット)
 │  └ lab-snet-private-dev-jpe (コンテナーサブネット / クラスターVM)
 ├ lab-nsg-dbw-dev-jpe
 ├ dev_dbw_lab (Premium, SCC, VNet injection)
 ├ lab-dbac-dev-jpe (Access Connector / SystemAssigned MI)
 └ labstucdevjpe (ADLS Gen2) / catalog-main
     └ カタログ dev_lab_10_main の storage_root

マネージドRG（自動生成）
 └ dbstorage... など（WS付帯。今回の表データ置き場ではない）
```

**public / private の名前は「インターネット公開」ではない。**  
製品用語で、ホスト用とクラスターVM用。SCC有効でも両方必要。

## Terraform のファイル分担

作業ディレクトリ例: `lab-databricks/`

| ファイル | 役割 |
|---|---|
| `providers.tf` | `azurerm` + `databricks`。WS URL を host に渡す |
| `variables.tf` | `subscription_id` など |
| `main.tf` | RG / VNet / NSG / サブネット / WS |
| `unity_catalog.tf` | Storage / Connector / RBAC / Credential / Location / Catalog |

`source = "hashicorp/azurerm"` は Terraform Registry 上のアドレス（誰のどのプロバイダか）。

`resource "..." "this"` の `this` はローカル名の慣習で、Azure上の表示名ではない。  
`{}` はモジュール専用ではなく、HCLのブロック括り。

### UC別建ての流れ（設計書4-3）

```text
ADLS Gen2 + container
 → Access Connector (MI)
 → RBAC (Storage Blob Data Contributor)
 → storage credential
 → external location
 → catalog (storage_root = 外部ロケーション)
```

ワークスペース自動生成ストレージは設定変更しにくい（特にパブリックネットワーク）。  
だからカタログ用ストレージを別にする。

## 構築コマンド

```powershell
cd lab-databricks
terraform init
terraform plan  -var "subscription_id=<SUB_ID>"
terraform apply -var "subscription_id=<SUB_ID>"
```

- `plan` … 何も作らない。差分の設計図
- `apply` … 実際に作成（確認プロンプトは `yes` のみ有効）
- `(known after apply)` … 作成後に決まる ID / URL

今回: **15 add**。所要は WS 作成が大半で数分〜10分程度。

### コスト感（目安）

| 状態 | 目安 |
|---|---|
| apply直後（クラスターOFF） | ほぼ誤差 |
| 最小クラスター起動中 | おおよそ 100〜150円/時 |
| 最後 | **必ず `terraform destroy`** |

## Azure CLI での確認（抜粋）

```powershell
# WS: Premium / SCC / VNet injection
az databricks workspace show -g lab-rg-dev-jpe -n dev_dbw_lab `
  --query "{sku:sku.name, enableNoPublicIp:parameters.enableNoPublicIp.value, vnet:parameters.customVirtualNetworkId.value, publicSubnet:parameters.customPublicSubnetName.value, privateSubnet:parameters.customPrivateSubnetName.value}" -o json

# サブネット委任
az network vnet subnet show -g lab-rg-dev-jpe --vnet-name lab-vnet-dev-jpe `
  -n lab-snet-private-dev-jpe --query "delegations[].serviceName" -o tsv
# → Microsoft.Databricks/workspaces

# Access Connector
az databricks access-connector show -g lab-rg-dev-jpe -n lab-dbac-dev-jpe `
  --query "{name:name, type:identity.type, principalId:identity.principalId}" -o table

# UCストレージが ADLS Gen2 か
az storage account show -g lab-rg-dev-jpe -n labstucdevjpe `
  --query "{name:name, hns:isHnsEnabled, sku:sku.name}" -o json
```

補足:

- `-o table` は列が少ない。ネスト（identity 等）は `--query` + json/table
- SystemAssigned MI … リソース専用の身分証。消すとIDも消える

## ハマりどころ

### 1. アカウントコンソールに入れない

`accounts.azuredatabricks.net` でテナントエラー。  
WSユーザーメニューにも Account console が出ない → **WS管理者 ≠ アカウント管理者** のことがあり、今回はスキップ。

WS本体（`https://adb-....azuredatabricks.net`）には入れた。

### 2. Databricks CLI × PowerShell の JSON

- bash 風 `'{"a":1}'` は壊れやすい
- `Set-Content -Encoding utf8` は BOM付きになり `invalid character 'ï'`
- 公式は **Compute UI で作って JSON をコピー** → `--json "@file.json"` を推奨  
  https://learn.microsoft.com/en-us/azure/databricks/dev-tools/cli/reference/clusters-commands

```powershell
databricks clusters create --json "@cluster.json"
```

### 3. `NO_ISOLATION ... not allowed`

UC必須WSではレガシーアクセスモード不可。明示する:

```json
"data_security_mode": "SINGLE_USER",
"single_user_name": "you@example.com"
```

### 4. VMサイズが使えない

`list-node-types` に名前があっても、`node_info.status` が `NotEnabledOnSubscription` なら実質不可。

| 例 | 状態（今回） |
|---|---|
| `Standard_F4s` | NotEnabledOnSubscription |
| `Standard_D4s_v3` | `node_info: {}`（使える側） |

在庫エラー時はサイズ変更や `ON_DEMAND_AZURE` も検討。

### 5. CLI の `clusters delete` は Terminate

```powershell
databricks clusters delete <CLUSTER_ID>
```

完全削除は `permanent-delete`。フラグは `--cluster-id` ではなく **位置引数**（新CLI）。

## 疎通確認（クラシックコンピュート）

クラスター例（シングルノード）:

```json
{
  "cluster_name": "cluster-lab-minimal",
  "spark_version": "15.4.x-scala2.12",
  "node_type_id": "Standard_D4s_v3",
  "num_workers": 0,
  "autotermination_minutes": 10,
  "data_security_mode": "SINGLE_USER",
  "single_user_name": "you@example.com",
  "spark_conf": {
    "spark.databricks.cluster.profile": "singleNode",
    "spark.master": "local[*]"
  },
  "custom_tags": { "ResourceClass": "SingleNode" },
  "azure_attributes": { "availability": "SPOT_WITH_FALLBACK_AZURE" }
}
```

これは **クラシックコンピュート**（VMを自分のVNetに載せる側）。  
サーバーレスは VMサイズを選ばず、Warehouseサイズや DBU で効能が決まる別物。

ノートブック（SQL）:

```sql
CREATE SCHEMA IF NOT EXISTS dev_lab_10_main.brz_sample;
CREATE TABLE dev_lab_10_main.brz_sample.hello AS
  SELECT 1 AS id, 'hub-domain-style' AS note;
SELECT * FROM dev_lab_10_main.brz_sample.hello;
```

SQL Editor の Connect は Warehouse 向き。クラシックなら **Notebook + クラスター接続** が確実。

### 実データは ADLS Gen2 へ

人間ユーザーに Blob Data RBAC が無いと `--auth-mode login` は失敗する。キーなら見られる:

```powershell
az storage blob list `
  --account-name labstucdevjpe `
  --container-name catalog-main `
  --auth-mode key `
  -o table
```

見えたパス例:

```text
__unitystorage/catalogs/<catalogId>/tables/<tableId>/
  _delta_log/...
  part-00000-....snappy.parquet
```

→ **カタログレベルのデータ分離（別建てストレージ）の体感完了**。  
マネージドRGの自動生成ストレージではない。

`information_schema` はメタデータ用の自動スキーマで、業務テーブルの置き場ではない。

### Spark Job が8個？

SQL3文でも、Delta書き込み・ログコミット・SELECT などで **Job は複数に割れる**。行数が少なくても異常ではない。

## コンピュートとクラスター

```text
Compute（総称）
 ├ Classic cluster   ← 今回
 ├ SQL Warehouse
 └ Serverless
```

クラスター ⊂ コンピュート。

数理最適化のような「1プロセス長時間・商用ソルバー・特殊環境」はクラシック寄り、軽い短時間の標準Pythonならサーバーレスも検討、という切り分けがしやすい（公式の核心数しきい値があるわけではない）。

## 片付け

```powershell
databricks clusters delete <CLUSTER_ID>   # 停止
terraform destroy -var "subscription_id=<SUB_ID>"
```

ポータルでリソースとコストが止まっていることを確認。

## 持ち帰ったこと

1. **触れないNSG** が、専用VNet／個別サブスク方針の技術根拠になっている  
2. **VNetインジェクション + SCC** は Terraform で再現しやすい  
3. **UC別建て**（Connector → RBAC → Credential → Location → Catalog）が手数の本体  
4. 表データはクラシック／サーバーレスどちらで書いても、マネージド表なら **catalog の storage_root（ADLS Gen2）**  
5. 私用ラボでも、CLIのBOM・SKU制限・アクセスモードなど「本番前に一度踏む系」の詰まりが出る
