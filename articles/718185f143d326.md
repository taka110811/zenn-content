Databricksからは、総合正答率や正解数そのものは通知されませんでした。

そこで、公開されている各分野の出題比率を使い、Topic Level Scoringを加重平均すると、次の計算になります。

```text
66% × 6%
+ 88% × 21%
+ 100% × 22%
+ 71% × 16%
+ 100% × 10%
+ 80% × 10%
+ 100% × 15%
= 88.8%
```

この計算では、**本番の正答率は約89%だったと推定できます**。

実際に画面へ表示された55問へ単純換算すると、次のとおりです。

```text
55問 × 88.8% = 48.84問
```

したがって、感覚としては**55問中約49問正解相当**です。

:::message alert
約88.8%および約49問という数字は、Databricksから通知された公式の総合点ではありません。

分野別スコアに公開されている出題比率を掛けた推定値です。分野別スコアの丸め、実際の分野別問題数、採点対象外問題の存在などにより、実際の正解数とは異なる可能性があります。

そのため、この記事では「正答率は約89%と推定」「55問換算では約49問相当」と表現します。
:::

先に結論を書くと、私の場合は次の流れが効果的でした。

1. Udemyの講義で試験範囲の全体像をつかむ
2. 模擬試験を解く

単に動画を一周するよりも、**模擬試験で迷った理由を言語化する作業**が最も重要だったと感じています。

## 特に間違えやすかったポイント

ここからは、私が模擬試験や本番前の復習で迷いやすかった分野をまとめます。

---

### Auto LoaderとCOPY INTO

どちらも、新しいファイルを増分で取り込む用途に使用できます。

| 比較項目 | Auto Loader | COPY INTO |
| --- | --- | --- |
| 主な用途 | 継続的・大規模なファイル取り込み | 比較的シンプルな増分ロード |
| 実行モデル | Structured Streamingベース | SQLコマンド |
| 状態管理 | Checkpoint | 読み込み済みファイルを追跡 |
| スキーマ進化 | 強い | 構成次第 |
| 大量ファイル | 適している | 規模によってはAuto Loaderが有利 |
| 実装の簡単さ | 設定項目が多い | SQLで実行しやすい |

重要なのは、「COPY INTOは重複を避けられない」と覚えないことです。

`COPY INTO`も、すでに読み込んだファイルを追跡し、同じファイルを再度取り込まない仕組みを持っています。

一方、`MERGE INTO`が防ぐのは、ファイル単位の重複というより、**キーに基づくレコード単位の重複や更新**です。

---

### Directory Listing ModeとFile Notification Mode

Auto Loaderが新しいファイルを検出する方法には、主にDirectory ListingとFile Notificationがあります。

| モード | 特徴 |
| --- | --- |
| Directory Listing | ストレージのディレクトリを確認して新しいファイルを検出 |
| File Notification | クラウドのイベント通知を利用して新しいファイルを検出 |

Directory Listingが向いている例は次のとおりです。

- 構成をできるだけ簡単にしたい
- 外部イベントサービスへ依存したくない
- ファイル数や負荷が極端に大きくない
- ファイル到着間隔が不規則でも、定期的なスキャンで問題ない

File Notificationが向いている例は次のとおりです。

- 大量のファイルを効率よく検出したい
- ストレージ全体のディレクトリ走査を減らしたい
- クラウド側のイベント通知サービスを構成できる
- 低遅延でファイルを検出したい

問題文に「外部イベントサービスへ依存しない」「最も簡単な構成」とあれば、Directory Listingが有力です。

---

### Lakeflow ConnectとLakehouse Federation

私は、SaaSアプリケーションからデータを取り込む問題で、Foreign Catalogと混同することがありました。

大きな違いは次のとおりです。

| 機能 | 目的 |
| --- | --- |
| Lakeflow Connect | データをDatabricksへ取り込み、Unity Catalog管理下のテーブルへ保存する |
| Lakehouse Federation | 外部システム上のデータへ、移動せずにクエリする |

SaaSデータを増分で取り込み、Databricks上のテーブルとして蓄積したい場合は、Lakeflow Connectが候補になります。

典型的な流れは次のとおりです。

1. Unity Catalog Connectionに接続情報を保持する
2. 取り込み元を設定する
3. 出力先のCatalogとSchemaを指定する
4. スケジュールや通知を設定する
5. Unity Catalog管理下のテーブルへ取り込む

Foreign Catalogは、外部データへ直接アクセスするLakehouse Federationの文脈で登場します。

---

### INSERT INTOとMERGE INTO

`INSERT INTO`は、基本的にはデータを追加します。

```sql
INSERT INTO target_table
SELECT *
FROM source_table;
```

既存レコードと同じキーを持つデータがあっても、そのまま追加すれば重複する可能性があります。

一方、`MERGE INTO`では、条件に一致するレコードを更新し、一致しないレコードだけを追加できます。

```sql
MERGE INTO target AS t
USING source AS s
ON t.transaction_id = s.transaction_id
WHEN MATCHED THEN
  UPDATE SET *
WHEN NOT MATCHED THEN
  INSERT *;
```

そのため、問題文に次の表現がある場合は`MERGE INTO`を検討します。

- 重複レコードを避けたい
- Upsertしたい
- 既存レコードを更新したい
- キーに基づいて挿入と更新を分けたい

---

### Managed TableとExternal Table

Unity CatalogにおけるManaged TableとExternal Tableの違いも重要でした。

| 比較項目 | Managed Table | External Table |
| --- | --- | --- |
| データの管理 | Databricksが管理 | 利用者が外部ストレージを管理 |
| ストレージ配置 | Managed Location | 明示した外部Location |
| テーブル削除時 | メタデータとデータが管理対象 | 通常はメタデータのみ削除 |
| 運用負荷 | 比較的小さい | ストレージ管理が必要 |
| 推奨される場面 | Databricks中心で管理する場合 | 外部システムとの共有や既存データを使う場合 |

要件に特別な制約がなければ、Unity Catalog Managed Tableを優先する考え方が基本です。

Managed Tableでは、Predictive Optimizationなどのマネージド機能も利用しやすくなります。

---

### OPTIMIZE、VACUUM、Predictive Optimization

この3つは役割が異なります。

| 機能 | 目的 |
| --- | --- |
| OPTIMIZE | 小さいデータファイルをまとめ、ファイル配置を改善する |
| VACUUM | 保持期間を過ぎた古いデータファイルを削除する |
| Predictive Optimization | テーブルの状況を分析し、最適化処理を自動化する |

`OPTIMIZE`は、ストレージ容量を直接減らすためのコマンドというより、**ファイルレイアウトを改善して読み取り効率を上げる処理**です。

`VACUUM`は不要になった古いファイルを削除します。ただし、削除したファイルを参照する古いバージョンへのTime Travelができなくなる可能性があります。

### DESCRIBE系コマンドとTime Travel

試験対策では、何を確認するコマンドなのかを整理しました。

| コマンド | 確認できるもの |
| --- | --- |
| `DESCRIBE HISTORY` | 過去の更新履歴 |
| `DESCRIBE DETAIL` | 現在のテーブルの詳細情報 |
| `DESCRIBE EXTENDED` | スキーマと拡張メタデータ |
| `VERSION AS OF` | 過去バージョンのデータ本体 |

例：

```sql
DESCRIBE HISTORY catalog.schema.table_name;
```

```sql
DESCRIBE DETAIL catalog.schema.table_name;
```

```sql
SELECT *
FROM catalog.schema.table_name VERSION AS OF 5;
```

`DESCRIBE HISTORY`は履歴を確認するためのものであり、過去データそのものを取得する構文ではありません。

### NOT NULL制約とCHECK制約

Delta Lakeで代表的な制約は、`NOT NULL`と`CHECK`です。

既存テーブルの列へ`NOT NULL`を設定する例です。

```sql
ALTER TABLE transactions
ALTER COLUMN transaction_id SET NOT NULL;
```

```sql
ALTER TABLE transactions
ALTER COLUMN transaction_date SET NOT NULL;
```

`CHECK`制約は、行が満たすべき条件を定義します。

```sql
ALTER TABLE transactions
ADD CONSTRAINT valid_amount
CHECK (amount >= 0);
```

複数列の関係も表現できます。

```sql
ALTER TABLE reservations
ADD CONSTRAINT valid_period
CHECK (end_date >= start_date);
```

`CHECK`は単にNULLを禁止するためだけではなく、値の範囲や列同士の整合性を保証するために使用できます。

### WHEREとHAVING

`WHERE`は集約前の行を絞り込みます。

```sql
SELECT department, COUNT(*) AS employee_count
FROM employees
WHERE status = 'active'
GROUP BY department;
```

`HAVING`は集約後のグループを絞り込みます。

```sql
SELECT department, COUNT(*) AS employee_count
FROM employees
WHERE status = 'active'
GROUP BY department
HAVING COUNT(*) >= 10;
```

集約関数を条件に使いたい場合は、基本的に`HAVING`を使用します。

### UNIONとUNION ALL

| 構文 | 動作 |
| --- | --- |
| `UNION` | 結果を結合し、重複を削除する |
| `UNION ALL` | 結果を結合し、重複を残す |

```sql
SELECT customer_id FROM online_customers
UNION
SELECT customer_id FROM store_customers;
```

重複削除が不要であれば、通常は`UNION ALL`の方が余計な重複排除処理を避けられます。

### JOINの種類

試験対策では、特に次のJOINを整理しました。

| JOIN | 残る行 |
| --- | --- |
| INNER JOIN | 両方に一致する行 |
| LEFT JOIN | 左側の全行と、右側の一致行 |
| RIGHT JOIN | 右側の全行と、左側の一致行 |
| FULL OUTER JOIN | 両方の全行 |
| LEFT SEMI JOIN | 右側に一致する左側の行だけ |
| LEFT ANTI JOIN | 右側に一致しない左側の行だけ |
| CROSS JOIN | 全組み合わせ |

LEFT SEMI JOINは、右側の列を結果へ追加するのではなく、右側に一致する左側の行だけを返します。

```sql
SELECT c.*
FROM customers c
LEFT SEMI JOIN orders o
ON c.customer_id = o.customer_id;
```

LEFT ANTI JOINは、注文履歴がない顧客の抽出などに利用できます。

```sql
SELECT c.*
FROM customers c
LEFT ANTI JOIN orders o
ON c.customer_id = o.customer_id;
```

### ROW_NUMBER

`ROW_NUMBER`は、グループ内の行へ順番を付けるWindow Functionです。

例えば、顧客ごとに最新の注文だけを取得できます。

```sql
WITH ranked_orders AS (
  SELECT
    *,
    ROW_NUMBER() OVER (
      PARTITION BY customer_id
      ORDER BY order_timestamp DESC
    ) AS row_num
  FROM orders
)
SELECT *
FROM ranked_orders
WHERE row_num = 1;
```

次の3要素を分けて覚えると理解しやすかったです。

- `PARTITION BY`：どの単位でグループを分けるか
- `ORDER BY`：グループ内でどの順番を付けるか
- `ROW_NUMBER`：各行へ一意な順位を付ける

### CTAS

CTASは、`CREATE TABLE AS SELECT`の略です。

```sql
CREATE TABLE catalog.schema.sales_summary
AS
SELECT
  customer_id,
  SUM(amount) AS total_amount
FROM catalog.schema.sales
GROUP BY customer_id;
```

CTASでは、SELECT結果をもとにテーブルを作成できます。

主なポイントは次のとおりです。

- SELECT結果から列名と型が決まる
- データを作成と同時に書き込める
- 既存データを変換しながらDelta Table化できる
- 外部テーブルにする場合は`LOCATION`などを明示する

### JSONの処理

試験直前に、JSON文字列から値を取得する構文を重点的に確認しました。

例えば、JSON文字列から特定フィールドを取得する場合です。

```sql
SELECT get_json_object(json_column, '$.customer.id') AS customer_id
FROM source_table;
```

構造を持つJSONとして扱いたい場合は、`from_json`を使用します。

```sql
SELECT from_json(
  json_column,
  'customer STRUCT<id: STRING, name: STRING>'
) AS parsed
FROM source_table;
```

使い分けのイメージは次のとおりです。

| 関数 | 用途 |
| --- | --- |
| `get_json_object` | JSON文字列から特定のパスを取り出す |
| `from_json` | JSON文字列をStructやArrayとして解析する |
| `to_json` | StructなどをJSON文字列へ変換する |

### Lakeflow Jobsの依存関係とRun if

Lakeflow Jobsでは、タスク間に依存関係を設定できます。

例えば次のような構成です。

```text
ingest
  ↓
transform
  ↓
publish
```

`Run if`は、上流タスクの結果に応じて、下流タスクを実行する条件です。

例として、次のような条件があります。

- All succeeded
- At least one succeeded
- None failed
- All done
- At least one failed

重要なのは、`Run if`がタスクの依存関係と無関係に動く条件ではないことです。

基本的には、設定された依存タスクの実行結果をもとに判定されます。

例えばエラー通知タスクは、上流タスクに依存させた上で、`At least one failed`を設定することが考えられます。

### Job Cluster、All-Purpose Compute、Serverless

Computeの選択問題では、単に「Serverlessが新しくて速い」と考えるのではなく、要件を見る必要があります。

| Compute | 主な用途 |
| --- | --- |
| All-Purpose Compute | 対話的な開発や分析 |
| Jobs Compute | ジョブ実行専用 |
| Serverless Compute | インフラ管理を減らし、迅速に実行 |
| Classic Compute | ネットワークや実行環境を細かく制御したい場合 |

問題文で次の表現があればServerlessが候補になります。

- インフラ管理のオーバーヘッドを減らしたい
- 起動時間を短くしたい
- DatabricksにCompute管理を任せたい

一方、次の要件ではClassic Computeが候補になる可能性があります。

- 顧客管理のネットワーク内で実行したい
- 特定のインスタンスタイプを制御したい
- 独自の初期化スクリプトや細かな構成が必要
- Computeリソースに対する詳細な管理が必要

### Driver、Executor、AQE、Broadcast Join

Sparkの処理を理解する上では、DriverとExecutorの役割を区別する必要があります。

| コンポーネント | 役割 |
| --- | --- |
| Driver | 実行計画の作成、タスクのスケジューリング、全体の調整 |
| Executor | 実際のデータ処理、キャッシュ、Shuffle処理 |

AQEはAdaptive Query Executionの略で、実行時の統計を利用してクエリプランを調整します。

主な最適化例は次のとおりです。

- Shuffle Partition数の調整
- Join方式の変更
- Skew Joinへの対応

Broadcast Joinでは、**小さいテーブルまたは小さいデータセット**を各Executorへ配布します。

「小さいファイルをBroadcastする」と覚えると誤りやすいです。

ファイルサイズではなく、Join対象となるリレーションの推定サイズが判断材料になります。

---

### CheckpointとWatermark

Structured Streamingでは、CheckpointとWatermarkの役割が異なります。

| 機能 | 目的 |
| --- | --- |
| Checkpoint | ストリーム処理の進捗や状態を保存し、障害後に再開する |
| Watermark | 遅れて到着するデータをどこまで待つかを定義する |

Checkpointは障害復旧やExactly-Once処理に関係します。

Watermarkは、イベント時刻ベースの集約で状態が無限に増え続けることを防ぐために使用されます。

## これから受験する人へのアドバイス

### 講義を完璧に暗記してから模擬試験へ進まない

動画をすべて覚えてから模擬試験を始めようとすると、時間がかかります。

最初に一周して全体像をつかみ、早めに問題演習へ進む方が、理解していない部分を見つけやすいと思います。

### 正解した問題も、迷ったなら復習する

偶然正解した問題は、本番では間違える可能性があります。

問題ごとに次の3段階で印を付けると復習しやすいです。

- A：根拠まで説明できる
- B：正解したが迷った
- C：不正解、または理解できていない

BとCを優先して復習します。

### 機能を単独で覚えない

Associate試験では、似た機能の比較が重要です。

例えば、次の組み合わせです。

- Auto Loader vs COPY INTO
- Lakeflow Connect vs Lakehouse Federation
- Managed Table vs External Table
- INSERT INTO vs MERGE INTO
- OPTIMIZE vs VACUUM
- Checkpoint vs Watermark
- Serverless vs Classic Compute
- WHERE vs HAVING
- UNION vs UNION ALL
- Row Filter vs Column Mask

「この機能は何か」だけではなく、「どの条件ならこちらを選ぶか」まで説明できる状態を目指すとよいと思います。

### 公式ドキュメントを根拠にする

模擬試験の解説が正しいとは限りません。

また、Databricksは機能名や推奨構成が比較的速く変化します。

疑問が残った場合は、公式ドキュメントや最新のExam Guideを確認することをおすすめします。
